### Background execution policy

On each scheduled check, identify the **served** version using a stable build/release marker or served static asset fingerprint, and corroborate with local `.next/BUILD_ID` only when it matches the running preview. An on-disk build or source edit alone is not publication. Store the last observed/tested fingerprint and case results in the release log section below. If version cannot be reliably identified, record that limitation instead of claiming a new release. If implementation/build is in progress or preview unavailable, defer live tests without restarting anything; notify once only when a persistent blocker requires action.

For each new stable version, inspect current capabilities and run the safe available slice: existing `npm test` in its temporary fixtures after checking it still isolates writes, authorized read-only browser/API smoke, login/error presentation, current upload/coverage UI, private-data denial, keyboard/zoom/mobile checks. Use separate QA browser profiles so tests do not sign out the user's session. Any upload/review/mapping/submission mutation requires a provisioned isolated synthetic QA application/account/database; do not alter the shared seeded demo. When isolation is absent, mark mutation cases BLOCKED and report that coverage gap once rather than claiming full acceptance. Do not run the legacy HTTP integration harness unchanged, new builds, migrations, seed/reset, restart checks, provider calls or database verification concurrently with active owners. Run broader existing checks only when their safe environment and exclusive window are established. No new test framework is required.

A green legacy SQLite unit suite does not prove the live PostgreSQL release. Tie each browser/API result to served version; tie unit results separately to inspected source fingerprint. Planned M2/M3 features are BLOCKED/not applicable to current release claims, never passed through simulated actions. Re-run failed cases after a changed version and include changed-feature regressions. Do not repeatedly run an unchanged version or rediscover the same known missing feature as a new bug.

Each bug report includes severity, CUJ/case ID, release/source identity, prerequisite/role, minimal reproduction, expected versus observed, redacted evidence, and whether it is a new regression or known gap. Do not log credentials, cookies, provider keys or real documents. Track recurring findings by stable ID and notify only on new/actionable bugs, a fix/regression, completed new-version testing, or a blocker needing user action. Remain quiet when nothing changed. This monitor detects and reports; it does not change app code, publish, message other chats or fix deployment configuration.

## Latest user priority: upload first, then match and show coverage

The user now prioritizes a **prominent global upload → optional model-assisted requirement matching → clear coverage** flow. This supersedes earlier acceptance criteria that removed or rejected a global upload button or required every file to start inside a request. Named uploads inside a focused request may remain useful secondary paths. docs/UX_REDESIGN.md is an earlier reference, not authority to reject this new direction.

A global upload saves original bytes before matching. A saved-but-unmatched file must remain visible, downloadable and actionable; it does not silently satisfy a request. With AI off, borrowers must be able to choose one or more requirements manually, change those mappings and continue the full manual workflow. Model suggestions are optional and explicitly unconfirmed until the borrower confirms or corrects them. A confirmed mapping expresses which request the file supports; it is neither a completeness finding nor lender acceptance. A file may support several requirements, and a requirement may need multiple files or periods. Partial evidence must leave the uncovered portion and next action visible.

These are updated acceptance targets, **not claims of implementation**. At the last source baseline, upload required one requirement ID, existing-file multi-mapping was not exposed, and AI was only a synthetic connection probe. Re-inspect the completed frontend and actual endpoints before classifying any target as implemented. A prominent upload control can pass its presentation check while unmatched storage/multi-mapping/AI remain product gaps. Do not require a fake AI suggestion or fake coverage state to make the new design look complete.

## Backend ownership update: queued analysis and active verification

The latest explicit user decision authorizes a dedicated backend owner plus a queue service/workers, including prioritization between upload-triggered background analysis and active **Verify completeness** requests. This supersedes earlier no-background-workers scope. Backend owns serving/job orchestration and Mastra/OpenRouter execution plumbing; AI owns prompts, extraction, matching, evidence and evaluations; database owns schema/repositories; platform owns Docker/runtime; frontend owns presentation. Do not independently select a competing queue, require a synchronous-only architecture, or change runtime services.

`docs/BACKEND_PLAN.md` is the forthcoming contract source; it was not present at this update's inspection. Its existence or planned queue is not implementation evidence. Before executable queue acceptance, align: job types and trigger/consent rules, durable enqueue boundary, application/file-version identity, idempotency, priority/fairness policy, active-Verify responsiveness target, retry budget/backoff, worker leases/timeouts, cancellation and stale-result conditions, observable user statuses, and which evidence revision a completeness result covers. Active Verify priority must be explicit and testable; do not assume preemption of already-running provider calls, fixed timing targets or starvation policy before agreement.

Until contracts align, queue cases below are **planned / BLOCKED**, not an invitation to expand implementation or start workers. M1 remains usable without AI credentials or model calls. Upload-triggered analysis must honor server-side application consent; opting out must prevent queued work from starting new provider calls and prevent stale/in-flight results from changing current mappings/coverage. Preserve original saved files through queue/provider failures. Turning AI on must not silently process historical files unless the agreed user-visible contract explicitly authorizes that action.

## Approved local deployment and ownership boundary

The **currently deployed baseline**, pending the platform-owned queue rollout, runs **PostgreSQL 17 only** in Docker Compose, with persistent `postgres_data` storage and loopback host port **5433**. Next.js runs on the host. The canonical browser and Better Auth origin is **http://127.0.0.1:3001**; use that origin consistently for login, cookies, redirects and mutation requests. Private uploads remain in the configured persistent local data directory outside public assets. This is neither a fully containerized application nor a public deployment. The new queue/worker decision may extend services through the platform owner after contracts align; this baseline is not a prohibition on that authorized work.

Platform owner alone owns Compose/runtime/environment/startup documentation and preview restarts. Database owner owns migrations/repositories; frontend owner owns presentation. Acceptance work must not independently change ports, auth origins, Docker services, dependencies or deployment architecture. Record conflicts for coordinator resolution. Never remove database volumes or reset the seeded demo. No disruptive build/restart while implementation is active. Auth remains required for M1 completion; a role switch or removal of sign-in cannot satisfy the gate.

AI credentials remain optional for M1 and must never appear in client code, logs or acceptance evidence. A no-credential run uses a platform-prepared isolated configuration; do not edit shared environment files or remove an existing key to perform that test.

Normal database restart acceptance is a separate scheduled step after implementation: platform owner performs the restart while retaining `postgres_data` and the upload directory; auditor captures authorized pre/post snapshots and download hashes. Do not run seed, delete/recreate volumes, or rebuild the app as a substitute for this check. During a planned database interruption, login must report failure without false success; when service recovers, retry must work. Browser-side network blocking may exercise generic request failure without interrupting the shared database, but is not evidence of actual database restart recovery.
