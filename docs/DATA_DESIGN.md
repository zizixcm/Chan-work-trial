## M1 conventions and small schema

Keep existing domain IDs as `text` (new IDs generated as UUID strings). This preserves every existing value without assuming all historical IDs parse as UUIDs; auth user IDs are also opaque text. Use UTC `timestamptz`, `date` for reporting dates, exact `numeric` for amounts/ratios, JSONB for bounded structured values/snapshots, and text plus CHECK constraints for evolving states. Expose decimal values as strings where precision matters; retain the existing requested_amount compatibility field only with documented dollars/units. No inferred cents conversion.

Every domain child carries application_id. Give referenced rows UNIQUE(application_id,id) and enforce composite foreign keys for every domain relationship, including optional references and join tables. A valid global ID alone must never permit cross-application linkage. Use RESTRICT deletion for evidence/history; omit domain hard-delete APIs in M1. Auth records follow the selected Better Auth schema; preserve actor labels even if a user is later disabled.

## Authorization boundary

Authenticate server-side with Better Auth on every read/write/download, then resolve active application membership. Request IDs and document IDs are untrusted selectors. Scope queries and joins to authorized application_id; enforce role before mutation. Session identity supplies actor fields; ignore user-supplied actor/role. Membership checks and business writes share the transaction so revocation cannot race a write (lock the membership row alongside the application). File reads check authorization immediately before resolving the private key; no raw paths/keys in public DTOs. Unauthenticated requests return 401; inaccessible objects return 404 consistently, role-denied actions on visible objects return 403.

| Capability | Borrower member | Lender member |
|---|---|---|
| Read application, checklist, permitted document versions and submission history | Yes | Yes |
| Upload, replace, map own application's evidence; add explanations/manual assertions; submit | Yes | No in initial portal contract |
| Add requirements; confirm reviewer facts; accept, waive, request changes | No | Yes |
| Read/write internal lender note | No | Yes |
| Change memberships or auth identity | No | No (explicit provisioning only) |

Lender application list filters by memberships; “lender” is not access to all applications. Retain same-origin mutation protections and auth library CSRF/session requirements. API authorization is required regardless of page visibility. RLS can be added later; do not claim it exists or use it as a reason to omit scoped repository methods. M1 access grants cover the whole application, including its guarantor documents; finer party-level access requires a later explicit product decision.

## Versioning, reviews and transitions

Serialize domain mutations by locking the application row first, then membership/requirement rows in a consistent order. Increment application.revision for every domain mutation. Increment application.content_revision for changes to draft package content (uploads, mappings, facts, explanations, findings, checklist definitions), but not for lender decisions/notes alone. Increment requirement.revision for every mutation affecting that request. Keep separate requirement.evidence_revision for changes to files, mappings, explanations, facts and findings that affect its review; requirement.definition_revision changes when its purpose/period/applicability changes. Review actions capture both input tokens and increment only the general revision. Thus saving a review does not immediately invalidate itself. Submission preview carries application.revision to detect concurrent lender actions as well as content changes; receipt also records content_revision for the borrower progress label. Return a newly computed projection after commit.

- Upload new document: version 1 in a new series; zero or more requirement links permit general uploads. Metadata and links appear only after bytes exist and the transaction commits.
- Replace: require expected head document ID; lock series, verify the predecessor is its latest version, insert N+1, then move active links from old to new version in the same transaction. Return 409 for competing replacements. Retain old links as unlinked and preserve old records/bytes. Explicitly show affected requests before replacing a multi-mapped file. Replacement is distinct from uploading an additional document.
- Duplicate hash: return 409 plus the existing authorized document ID; offer linking the existing file to another request. Do not add an identical new version. Detect only within the application, preventing information leakage across applications.
- Mapping changes and replacement invalidate acceptance for affected evidence; unrelated request uploads do not. Review evidence must match the exact version-ID set and revisions of its declared current/submission scope. A lender can accept active evidence before a package is submitted; submission_id is required only for submission scope.
- Append review actions, never edit old decisions. Accept requires evidence appropriate to response_mode: intact linked files for documents, a nonempty explicit explanation for explanation, or either for either. Pin explanation revisions as well as file IDs. Waive can apply with no file and always needs a reason. Change request needs a reason. A new current-scope review supersedes the current decision, not the history. Historical-scope decisions remain attached to their package and never override newer draft decisions.
- Waiver is a lender decision about the requirement itself: remains effective through borrower evidence changes; explicit lender request-changes or acceptance supersedes it. Requirement policy/period edits require explicit reconsideration and invalidate waiver. Store the applicable requirement definition revision with a waiver to implement this rule.
- Requirement lifecycle is active → superseded, with reason/audit. Do not delete obsolete conditional requests or reopen them silently. Rerunning the same rule/evidence reuses the active occurrence for its condition_key. If a condition clears, supersede that occurrence; if it later recurs, create the next occurrence linked to the previous request, with a visible reason. A materially changed input set creates a linked finding revision.

Derived UI states, not one overloaded persisted status: `Not uploaded` or `Response needed` according to response_mode (active request, no evidence); `Uploaded` or `Response provided` according to response_mode (evidence without current review or submission coverage); `Waiting for lender review` (latest submission contains the current evidence revision); `Changes requested` (latest applicable lender action); `Accepted by lender` (latest acceptance matches evidence and definition revisions); `Waived by lender`; `Superseded`. If new evidence arrives after changes_requested, show Uploaded plus the prior lender reason until reviewed. An explanation alone never means accepted. Define precedence: superseded, effective waiver, current review, current submission coverage, evidence presence, missing. Application lifecycle uses the explicit workflow events and submission history defined under Workflow and migration acceptance additions below. Independently, compare content_revision to the latest submission to show whether the draft has changes; general revision remains the concurrency token.

## Immutable handoff and concurrency

Preview first reconciles applicable deterministic checks in a committed transaction, then returns the resulting application revision, effective date, policy timezone and preview hash. Submit takes that preview token, acknowledgment of every current gap/exception, and an idempotency key. Under the application lock, validate membership, the unchanged preview inputs/date and stored file availability/integrity. If anything changed, end the submit attempt without creating a handoff, reconcile and commit a fresh preview in a separate transaction, then return 409 and require renewed acknowledgment. Never roll back the refreshed findings while returning a token that claims they persisted. The request retries must not silently acknowledge new exceptions. A missing requested document can be an acknowledged exception; missing/corrupt bytes for a supposedly included file require repair or explicit removal from the draft before handoff.

In the same transaction, allocate revision_number, freeze the manifest, insert its file references, and audit submission. Receipt returns id, revision number, timestamp and hash. Reusing the same key with the same request returns the original receipt; a different payload with that key conflicts. Do not derive sequence as unlocked MAX+1.

Manifest v1 includes copied application/LOI/checklist context; requirement definitions and lifecycle; exact document IDs, versions, names, MIME, size, SHA-256 and mappings; facts and confirmation/provenance; findings and rule/input snapshots; explanation revisions; latest review decisions and their evidence scope; acknowledged unresolved exceptions; submitter label/time. Construct the canonical manifest from an explicit allowlist excluding internal notes, credentials and storage keys entirely; do not embed them and rely on later redaction. JSON content is validated against a versioned TypeScript runtime validator. Hash canonical serialized bytes, preserving canonical serialization/version for repeatable verification.

No rendering of an old submission may join current mutable descriptions or current mappings to reconstruct its historical truth. Read the frozen manifest and referenced immutable files. Subsequent review actions link to the submission but do not rewrite it. Resubmission inserts N+1; no submitted→draft mutation of an existing receipt. Protect submissions and immutable domain rows with database permissions/triggers rejecting UPDATE/DELETE for the app role; migrations use a separate role. A checksum detects changes but is not an adversary-proof signature.

## Confirmed facts and deterministic checks

Manual entry is an assertion until the borrower explicitly confirms it or a lender enters/confirms it. Store units, reporting period and exact source version/location; unknown is null/needs_clarification, never zero. Preserve correction history using supersedes_id and reject concurrent correction of the same head. Only latest eligible confirmed facts feed ordinary rules. Conflicting confirmations require clarification, not last-write-wins selection without explanation. A borrower correction of evidence-derived information remains an assertion unless explicitly confirmed; future disputed AI facts may drive a clearly provisional result, not lender acceptance.

Pin rule version and configuration plus effective date, input fact IDs/values and provenance in every finding. Fingerprint includes the rule/config version, all input revisions, and time-sensitive evaluation date. R1 two-calendar-month inclusive cutoff; R3 >=35%; R4 >50% with positive net worth; R6 relative decline >=30%, positive comparable denominators. Use decimal arithmetic or exact scaled values to avoid floating-point boundary errors. Unknown/future dates and invalid denominators produce clarification. R2 needs explicit vacancy; missing tenant name is insufficient. M1 R5 is lender-entered schedule applicability/missing-evidence information, never claimed automatic document parsing. All thresholds remain the provisional policies in REQUIREMENTS.md.

## Incremental migration and dependency order

1. **Contract agreement:** coordinator accepts library choice and revised DTOs/command signatures. Platform pins dependencies/auth configuration, creates Docker PostgreSQL volume and private upload configuration; portal can implement against typed fixture contracts. Keep M1 startup independent of any AI environment variable.
2. **Schema foundation:** create a separate PostgreSQL migration directory/ledger. Preserve SQLite SQL untouched. Create auth, applications/memberships, requirements/series/documents/mappings/audit first; then explanations/facts/findings, reviews/notes and submissions. Review cyclic nullable references in a follow-up ALTER migration. No auto-seeding in repository constructors. Explicit synthetic seed is idempotent and does not overwrite user changes.
3. **Import rehearsal:** freeze writes in the old app and close SQLite connections; take a consistent SQLite backup including committed WAL state via SQLite backup/checkpoint procedure, and a file-directory backup. Never copy only an actively written portal.sqlite. Export every row, SQLite review rowid/order, migration ledger and raw timestamp/JSON strings into a private import artifact with source checksum. Do not inspect/log credentials.
4. **Preflight:** verify foreign keys, duplicate keys, JSON review IDs and that all referenced documents belong to the same application. Inventory every storage key, byte count and SHA-256 against actual files. Report missing/corrupt bytes and abort cutover until reconciled; do not silently discard rows or files. Existing repository does not enforce cross-application review references at the SQL level, so validate explicitly. Validate timestamp parsing and preserve original text in import provenance if formatting changes.
5. **Transform without invention:** import original application/requirement/document/review/audit IDs and timestamps exactly in meaning. Create one deterministic new series per existing document, version 1, no predecessor: the old data does not identify replacements. Preserve all old mappings as active. Copy existing review document_ids into review_documents and retain original JSON in import provenance. Preserve review ordering with per-requirement sequence based on old rowid; do not infer order solely from timestamp. Import notes as current bodies, with no fabricated prior bodies. Preserve all historical display labels; no automatic identity attribution. Existing audit order uses exported rowid as deterministic sequence.
6. **Compatibility state:** imported reviews are applicable only when their recorded set matches active linked files; mark unmatched evidence scope historical/stale. Initialize revisions and definition/evidence tokens consistently with this condition. Preserve legacy labels/transaction strings in data; normalize only through explicit DTO mapping. Seed Better Auth demo identities through supported auth APIs and explicitly grant memberships separately. Do not convert old actor names into passwords or fake sessions.
7. **Atomic target import:** load into an empty target or transactionally tagged import batch, with import ledger keyed by source backup checksum and row counts. Retry returns the same result; conflicting already-imported IDs abort instead of overwrite. Compare sorted primary-key sets, relationship counts, review order, legacy field values and all file hashes. Preserve original storage keys and root, or copy bytes to the new configured root under the same keys and verify both copies. No filename conversion/re-encoding. Save a reconciliation report privately without document content.
8. **Adapter cutover:** run PostgreSQL repository through existing validation/storage/service paths. No dual writes. Stop SQLite-backed server before enabling target writes. Switch configured adapter only after verification; never silently fall back to SQLite on PostgreSQL errors. Retain read-only source backup, import artifacts and original files. Rollback before target writes is a configuration restore; after new target writes it requires exporting/reconciling those records first, not switching back and losing them.
9. **M1 completion:** integrate portal flows/auth, immutable submissions, deterministic rules and scoped download checks. Run preserved checks and manual journey below. Record actual outcomes in README by its owner. Migration script/setup commands and destructive reset behavior are explicit; normal restart never seeds/resets existing records.

File/SQL atomicity is not possible across two independent stores. Write unique durable bytes first; commit metadata/links/audit second. Compensate known failed transactions. A lost commit response must be resolved through the idempotency record before deleting bytes: do not delete a file merely because the client saw an error. Crash leftovers are unreferenced files; provide an explicit reconciliation/cleanup command with a grace period, not a worker. Never remove referenced old versions. Disk full/checksum mismatch produces a failed operation and actionable recovery, never a successful upload indicator. Storage and PostgreSQL volume backups must be coordinated.

## Review refinements — implementation invariants

These refinements resolve ambiguities found by three independent design reviewers. They are proposed M1 requirements for this schema, not claims that the current implementation enforces them.

### Evidence and revision integrity

- Document predecessor must belong to the same application **and series**. Enforce one root per series with a partial unique index; root is version 1 with no predecessor. All later versions must point to version N−1. A transactional insert function/trigger validates this under a series lock; the same-series FK alone does not guarantee a linear chain. Immutable rows prevent retroactive cycles.
- An identical-byte upload remains a duplicate, including an old version. For M1, offer linking the existing version explicitly, with a visible historical-version label and normal review invalidation; do not create a new version or silently move a series head backwards. Current request mappings may explicitly use historical versions; “latest uploaded” and “selected evidence” are different concepts.
- Add `review_explanations(application_id,review_id,explanation_id)` with composite FKs. A lender can accept a text-only clarification request (for example DSCR decline) according to response_mode; a document-only request still requires a file or an explicit waiver. Review snapshots pin both definition_revision and evidence_revision plus exact file/explanation IDs.
- `review_scope=current` validates current request tokens and selected evidence. `review_scope=submission` requires submission_id and validates against that submission's frozen request/evidence snapshot. A historical submission review never accepts newer draft evidence. Display it as historical when its scope differs. Membership authorizes the action now; the snapshot determines what was reviewed then.
- Protect immutable parent records **and their membership tables**: review_documents, review_explanations and submission_documents cannot be appended, updated or deleted after their parent is sealed. Insert the complete aggregate via a transaction/function, mark sealed before commit, and reject later mutations. Restrict direct app-role writes so callers cannot bypass sealing. Freezing only the parent JSON while allowing attachment changes is insufficient.
- For the one canonical submission representation, canonical_manifest is the serialized source and manifest is its validated JSONB projection. At sealing, verify parsed equality, checksum, unique document IDs, matching relational attachment set, same-application ownership and acknowledgment references. Do not let independent serializers construct the JSON, canonical text and joins. Specify canonical UTF-8 encoding, object key ordering, decimal-string representation and sorting of unordered arrays by stable IDs; verify hash over those exact bytes.

### Facts, subjects and dependency tracking

Use a small `application_subjects(application_id,id,kind,label)` table for stable property, borrower, guarantor and tenant identities. It is not a reusable portfolio/entity graph. Reference these identities from requirements/facts and freeze labels in submissions. Tenant names alone are not stable identifiers.

Add fact lineage identity (`fact_series_id`, revision_number), where the immutable series key is application + subject + fact_key + unit + period/as-of scope + assertion author/source context. Distinct authors can make competing assertions about the same fact slot; a recorded reviewer resolution selects applicable evidence or leaves clarification pending. Corrections/confirmation append within that series, require its expected head and cannot branch or switch subject/period. An asserted correction within an existing series makes its older confirmed head ineligible; do not search backwards and resurrect a superseded confirmed value. Explanations similarly require a stable series/context/author and single successor per revision. A new period is a new series. Unknown dates need explicit scope identifiers, not accidental duplicate NULL keys. Store normalized decimal strings and typed runtime validation inside fact JSON; do not accept arbitrary objects as numeric inputs.

Add `finding_facts(application_id,finding_id,fact_id)` and `fact_sources(application_id,fact_id,document_id,location)` with composite FKs; they pin relational evidence while input_snapshot retains the exact values/configuration. A document replacement does not automatically transfer confirmation to its new bytes. Mark dependent current facts/findings ineligible in the derived projection, require reconfirmation/new facts or an explicit reviewer decision retaining historical evidence, and invalidate affected request review tokens transactionally. Unrelated facts remain eligible. Include subject/scope in finding identity and fingerprint. For time-independent rules exclude the clock from fingerprints; only time-dependent rules such as freshness include the effective date. Store application policy_timezone and use it to derive the effective date; for calendar-month subtraction clamp to the last valid day of the destination month. Seed the timezone explicitly rather than using host-local time. Repeating a run with identical inputs must be a no-op, not continually increment revisions and make submission impossible.

### Upload retries and draft inclusion

Add `mutation_receipts(application_id,actor_user_id,operation,idempotency_key,request_hash,result JSONB,created_at)` with a unique composite key on application/actor/operation/key. Commit it in the same transaction as the successful domain mutation. Authenticate and authorize before receipt lookup; replay identical successful requests before stale-revision checks, and reject changed request hashes. The hash covers file checksum/length, selected mappings, predecessor and relevant command fields. This supports upload/replace/submit retries and resolving an unknown commit outcome. On unknown outcome, retain bytes until a fresh database connection resolves the receipt; database unavailability is not permission to delete them.

Add `draft_document_selections(application_id,document_id,included,updated_by,updated_at)` for unmapped uploads; linked active request evidence is included automatically. Snapshot inclusion is active linked versions plus explicitly included general uploads, deduplicated. To omit a corrupt or irrelevant file, unmap it and exclude its general selection, recording the change and any resulting gap. This does not delete historical bytes or submitted references. General uploads must have an explicit include/exclude choice in the submission preview. Selection changes increment content_revision.

### Authorization and history visibility

Borrowers may append/supersede their own explanations and assertions; they cannot overwrite another actor's response or supersede a lender-confirmed fact as if it were lender-confirmed. A challenge to another actor's fact is a new linked assertion/correction request, visible to the reviewer. Lender confirmation records its own actor and preserves the borrower's source. Authorization rechecks occur inside writes; actor_kind (user/system/legacy_import), role-at-action and display-name-at-action are saved with every new review, explanation, confirmation and audit entry. System rule events retain the initiating user when available but identify the rule engine as the actor; they do not impersonate lender judgment. Historical user-ID fields remain nullable only for imported records with explicit legacy provenance.

Membership grants, role changes and revocations are auditable transactions, even when invoked only through local provisioning. Lock application then membership consistently for both provisioning and ordinary commands. New actions need an active membership; historical attribution references a durable user identity, not the mutable current membership role. Disable users rather than cascade-delete domain history.

Raw audit records are lender/admin-only; borrowers receive an explicit allowlisted activity projection. Use an explicit event visibility classification (`borrower_visible` or `lender_internal`) and field allowlists in all history serializers. Internal note bodies never enter general borrower audit DTOs, submission snapshots, fact evidence or later escalation context. Keep note revision history in a lender-only table or tightly scoped internal events. Borrower-visible audit descriptions cannot reveal hidden action payloads through generic JSON serialization. Downloads authorize at request start; revocation blocks subsequent requests but cannot recall bytes already delivered. Use no-store responses; old receipt links confer no independent access. M1 grants access to all application evidence (including draft/unlinked files and prior versions) only for the synthetic demo; scoped guarantor access remains a gate before real borrower use, as REQUIREMENTS.md states.

### Workflow and migration acceptance additions

Persist explicit application workflow events for review-started, follow-up-requested and collection-completed, with actor, time and basis submission ID/revision. Derive Collecting/Submitted/In review/Follow-up requested/Resubmitted from these events and submissions; retain “draft has changes” as a separate flag. Collection complete requires an explicit lender action against a current submission with all active requests accepted/waived; it is never loan approval. Later material changes reopen collection through a recorded event. No single general mutation counter can faithfully represent this lifecycle.

Separate a fresh synthetic seed from the lossless legacy importer. Import all applications and audit rows from the frozen source, preserve source row order/provenance, compare counts and values, verify byte hashes, and retain missing-history disclosures. Never use the old repository constructor as an importer because it runs migrations/seeding on the source. A pre-existing target application does not prove an import completed. Record an import batch checksum/state and reject collisions or incomplete reconciliation. Apply new PostgreSQL migrations forward; do not rewrite an already-applied migration to match this proposed design.

Additional acceptance cases: stale request period with unchanged files; two explanations racing to supersede one head; text-only acceptance; a rule clearing and recurring; selecting a historical version intentionally; review of submission 1 after draft/submission 2 exists; post-seal attachment insertion denied; omitted general upload not blocking submission; repeated rule run not changing revisions; response loss after commit; borrower attempting to supersede lender-confirmed facts; membership revocation racing a write; internal note details absent from every borrower history/submission endpoint.

Review outcome: all three reviewers completed read-only reviews. Their substantive M1 findings were incorporated above. The original M1 review did not require a generic workflow engine, full event sourcing, portfolio graph or AI/chat tables. The later approved queue/worker direction supersedes its original no-background-workers assumption. New application workflow events are a narrow audit of explicit review/collection actions. This is a reviewed design contract; executable migrations, SQL constraint checks and end-to-end behavior remain to be implemented and verified.

## Upload-first matching and visible coverage — proposed additive contract

Latest clarified direction: borrowers may optionally link files themselves **or let opted-in AI create links**. Human confirmation is not required for every model-created link. Save documents before matching; ambiguous matches remain suggestions. This supersedes the earlier confirmation-only proposal. This section is a plan, not an implemented migration/API change.

### Verified support and smallest delivery sequence

The installed schema already permits documents with no requirement links and many-to-many mappings through `requirement_documents`, with application-scoped foreign keys and active/unlinked history. The current `saveUpload`, `DocumentRepository.insert`, `PostgresRepository.insert` and POST `/api/documents` interfaces still require one requirement ID. Making selection optional needs service/API changes, not relaxation of database integrity.

1. Normalize optional `requirementIds: string[] = []`; retain legacy requirementId as a compatibility input and reject ambiguous combinations. Save bytes, document metadata, optional human links, draft_document_selections(included=true), audit and mutation receipt before returning upload success. No model call belongs in that transaction or is necessary for success. A duplicate checksum returns an authorized existing-document reference so matching can continue without another file/version.
2. Keep manual linking/unlinking available with AI off. A human can map one file to several requests, or several files to one request, without asserting completeness. Unassigned uploads stay visible and can be explicitly included/excluded from submission; exclusion from general selection does not silently remove an active requirement link.
3. When AI is opted in and the configured matching policy permits it, validated model matches can become active links directly. Each appears as “Linked by AI,” with its reason/evidence and an easy change/remove action. Ambiguous or unsupported matches remain visible proposals. Do not describe model links as human-confirmed or lender-approved.
4. Derive coverage separately using explicit scope and attributed evidence. Missing coverage specifications produce unknown completeness, not a percentage inferred from file count or confidence.

Use the next unused forward migration number when implementation is assigned. Preserve all existing IDs/links and never invent historical user confirmations.

### Rules for creating and correcting links

A model-created link is allowed only after schema validation and the application's opt-in matching policy checks. Persist the policy version and the basis for auto-link eligibility; no invented universal confidence threshold is specified here. A confidence number alone cannot establish the correct borrower, reporting period, document identity or request. An unsupported format, missing evidence, conflicting candidate or uncertain applicability yields a suggestion needing review.

After the provider returns, acquire the application lock and recheck active initiating membership, application ownership of every target, exact document/version/hash, current applicable requirement definitions, AI preference epoch and run status. A replacement, changed relevant requirement, disabled AI or revoked membership prevents late link application. Persist the stale/failed outcome separately; never undo the saved upload. Use validated current state, not untrusted model-generated IDs, roles, SQL or instructions embedded in a document.

Apply a validated batch by appending model link events, inserting/reactivating the corresponding active relation, incrementing affected evidence/application revisions and writing audit records in one transaction. Reuse mutation_receipts or a unique run-application operation key to make retries idempotent. Existing active links are deduplicated: a rerun does not relink, change attribution, increment revisions or invalidate acceptance merely for agreeing with an existing mapping. A new human confirmation of an AI link is an explicit event; it may change attribution of the user's decision but must retain the original model event.

Human actions take precedence over model actions. Changing/removing/rejecting a link records an immutable event and changes the mapping projection atomically. The user can edit an AI link as easily as a manual link. A model may propose alternatives but must not silently remove human links or undo human corrections. Do not infer that uploading from a general file area authorized every possible model association when AI is off.

A human reject/unlink suppresses automatic recreation for the same application, document version/hash, requirement and definition revision. Match this suppression across analysis-run IDs, prompt/model changes and retries; a new run is not new evidence. Store a stable evidence_fingerprint separately from the run identifier. Materially new bytes or a materially changed requirement may produce a new candidate with an explanation of what changed; following a prior rejection, present that candidate for review rather than silently restoring the removed link. Explicit human relinking clears the active suppression through a new event, without deleting history.

Confirmed human links and active model links both count as **associated evidence** in the current package. Neither is lender acceptance. Mapping changes increment the affected request evidence revision, making prior acceptance historical under the existing review rules. Repeated suggestions, rejected proposals and duplicate no-op links do not change evidence revisions. Replacement never silently transfers provenance or completeness to new bytes: any carried-forward mapping is an explicit replacement decision or a newly validated model action, and old events remain attached to the original version.

### Visible association, coverage and review

Expose independent fields rather than a single misleading status:

- Association: unassigned or linked, with per-link origin (human/model/legacy), reason and pending suggestions. One document can have active links and additional ambiguous proposals simultaneously. Human-confirmed is an optional event-derived label, not a prerequisite for a link.
- Coverage: unknown / partial / reported_complete, plus covered/missing/unknown criterion IDs and assessment origin. Clearly label AI-assessed coverage separately from human assertions. Do not label model claims as confirmed facts.
- Review: not_reviewed / changes_requested / accepted / waived, from explicit scoped lender decisions only.

For defined criteria, union evidence-supported criterion claims across active links, deduplicate and compare with the required set; keep model-assessed and human-confirmed provenance visible. Conflicts produce clarification/unknown. Do not add percentages across files or combine different periods/parties to manufacture completeness. Without a coverage_spec, show linked files and “Coverage needs review.” A model saying “complete” cannot manufacture an unspecified denominator.

Example: the request asks for 2024 and 2025 operating statements. AI may link an uploaded 2024 statement and report one of two periods covered, clearly labeled as AI-assessed. A second 2024 statement does not increase the count. A 2025 statement may complete the reported period coverage. The lender must still assess and explicitly accept the evidence. A manual association alone also does not assert the correct period or complete contents.

Coverage claims are not financial facts used by deterministic rules. Extracted values continue through the separate facts/confirmation model. Lender acceptance/waiver remains a distinct judgment and does not arise from model confidence, link count or coverage percentage.

## Queue/worker scope update — contract alignment pending

The user has explicitly approved a queue service and workers, including prioritization between upload-triggered background analysis and active “Verify completeness” requests. This supersedes the earlier no-background-workers/request-driven-only assumption. It does not change the requirement that upload bytes/metadata are saved durably before analysis, that AI is opt-in, or that model output cannot create lender acceptance.

Ownership is explicit: backend owns serving/job orchestration and Mastra/OpenRouter execution plumbing and will define docs/BACKEND_PLAN.md; AI owns prompts, extraction, matching, evidence and evaluations; database owns schema/repositories; platform owns Docker/runtime; frontend owns presentation. No competing queue, broker, worker service or synchronous-only replacement will be introduced here. Queue-specific implementation and migrations wait for the shared contract.

The database review of that contract must resolve these boundaries before implementation:

- Keep logical analysis runs/results separate from job delivery and execution attempts. Identify whether one run is reused for equivalent upload/Verify work, how a user-requested verification waits on or supersedes in-flight work, and which state/result the UI observes. Do not conflate duplicate delivery with a new business analysis.
- Define workload classes for upload-triggered analysis and active Verify requests, plus priority/promotion, bounded fairness, cancellation and timeout semantics. Backend owns scheduling; the database supplies agreed state transitions and atomic repository operations. No numeric priority scheme is assumed yet.
- Define an atomic enqueue boundary. If the chosen queue cannot share the document transaction, agree a durable handoff/outbox mechanism and reconciliation owner. Do not claim a job is durably queued merely because bytes were saved or an enqueue call was attempted. Queue failure must leave the file usable and retryable.
- Define leases/attempt identity and a fencing token for committing results. An expired/retried worker must not overwrite a newer attempt, apply duplicate links or complete a canceled run. Use idempotent result/mapping commits with database uniqueness and compare-and-set guards; do not promise exactly-once provider execution.
- Carry exact document version/hash, relevant request-definition/checklist fingerprint, AI preference epoch and initiating user identity into the run. Recheck authorization, opt-in and input eligibility before external processing and again before applying results. Do not persist browser sessions/cookies as worker credentials.
- Persist recoverable queued/running/retrying/failed/canceled/stale/completed semantics as agreed with backend, including timestamps, safe errors and retry ownership. The prior “mark interrupted on next page read” proposal is not the new worker recovery contract.
- Preserve human mapping removals/rejections and evidence-scoped suppression through retries, priority changes and duplicate deliveries. Only validated eligible model matches may become active links; ambiguous matches remain proposals. Result commits, mapping provenance, audit and evidence revisions must be atomic.
- Verify upload durability when enqueue/provider execution fails, priority behavior under contention, worker restart/lease expiry, duplicate delivery, stale attempt completion, AI-off/revocation while queued/running, replacement during analysis, human correction before retry, and independent manual workflow availability.

The selected queue technology, deployment topology, final job/run schema, worker credentials, retry limits and completion API are pending backend/platform alignment. This update changes design guidance only; it adds no dependencies, migrations, services or provider calls.
